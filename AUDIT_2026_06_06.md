# Production-Readiness Audit — Ruhestandsplaner Pro

**Datum:** 2026-06-06
**Auditor:** Senior Architect / Full-Stack / Security / QA Lead
**Scope:** `/workspace/retirement-planner` — gesamte Codebasis
**Deployment-Ziel:** `app.veyder-malberg.com` (Vercel) für österreichischen Private-Banking-Einsatz
**Standard:** Bank-grade „Golden Standard" — stabil, performant, sicher, wartbar, elegant.

---

## 1. Verständnis der App

### 1.1 Zweck
Ein Web-Tool für Private Banker, mit dem sie gemeinsam mit Kunden eine **Ruhestandsplanung** durchführen:
- Erfassung von Kundenprofil (Alter, Vermögen, Risikoneigung)
- Konfiguration eines **Drei-Topf-Portfolios** (Cash / Bonds / Equities) plus optionalem Private-Equity-Bucket
- **Monte-Carlo-Simulation** (10 000 Pfade, korrelierte Renditen via Cholesky)
- **Historische Rückrechnung** (1900-heute) und **MiFID-II-Szenariovergleich**
- **KESt-Logik** (27,5 %, österreichisch, mit High-Watermark)
- **Liquiditätsereignisse** (Erbschaft, Immobilienverkauf etc.)
- **Pension** als zweite Einkommensquelle
- **Bestände-Direkteingabe** (ISIN/Ticker via Yahoo + OpenFIGI Backtest)
- **Export**: PDF/HTML-Kundenreport (Skeena-Hausschrift), Excel, PowerPoint
- **Zwei UI-Modi**: „Klassik" (Beratung am Tisch) vs. „Pro" (alle Werkzeuge)

### 1.2 Kernnutzer
| Persona | Bedürfnisse | Erwartung |
|---|---|---|
| **Senior Private Banker** (Hauptnutzer) | Beratungsgespräch in 60–90 Min, repräsentativer PDF-Export, schnelle „Was-wäre-wenn"-Szenarien | Eleganz, Fokus, Vertrauen, Zero-Frustration |
| **Junior Banker / Trainee** | Lernen, sich mit Edge Cases vertraut machen | Klare Erklärungen, Tooltips, Training |
| **Kunde** (Co-Pilot) | Sieht Bildschirm während Beratung | Klare Visualisierung, keine technischen Begriffe |
| **IT-Compliance** | Bank-Sicherheits-Mindeststandards | CSP, kein externer Egress, Logging, Audit-Trail |

### 1.3 Wichtigste User Flows
1. **Profile → Eingaben → Portfolio → Simulation → Ergebnisse → Export** (Hauptpfad, ~80 % der Zeit)
2. **Szenariovergleich**: Multi-Run über 4 MiFID-Profile (~10 %)
3. **Holdings-Backtest**: ISIN/Ticker eingeben → 20-Jahre-Backtest (~5 %)
4. **Detailpfad**: Einzelnen Monte-Carlo-Pfad mit Trace nachvollziehen (~3 %)
5. **Wieder aufnehmen**: Banker kommt nach Pause/Termin zurück → erwartet seinen Stand wieder (heute: **verloren** ⚠️)

### 1.4 Annahmen (begründet, nicht rückgefragt)
| # | Annahme | Begründung |
|---|---|---|
| A1 | Single-Tenant (eine Bank, kein Mandanten-Modell) | `defaults.ts` hat nur einen `defaultAdvisor`, keine User-DB |
| A2 | Kein User-Login bisher → Zugriff über VPN/Intranet bzw. Vercel-Auth-Wall | Es gibt weder NextAuth noch Cookie-Sessions im Code |
| A3 | Daten bleiben Client-seitig — keine Persistenz auf Server | Es gibt keine DB-Migrationen, kein `prisma/schema.prisma`, trotz `prisma generate` im Build |
| A4 | Die App muss DSGVO/GDPR-tauglich sein | Bank-Kontext, Kundendaten = personenbezogen |
| A5 | Sprachen DE primär, EN sekundär | i18n-Keys vorhanden, beide vollständig gepflegt |
| A6 | „Vorzeitige Pension" ist erlaubt: pensionStartAge < retirementAge | Der jüngste Bug betraf genau diese Trennung |
| A7 | Yahoo Finance ist als unverbindliche Marktdatenquelle akzeptabel | Bestehender Code nutzt Yahoo + OpenFIGI ohne Vendor-Vertrag |

## 2. Audit nach Dimensionen

### 2.1 Architektur und Code-Struktur — **Note 2 (gut, mit Schatten)**
**Stärken:**
- Klarer App-Router-Aufbau (`src/app`), Komponenten in `src/components/sections/`, Engine isoliert in `src/lib/engine/`.
- `runMonteCarloSimulation` ist eine reine Funktion (kein State) → testbar und portierbar (z. B. in einen Worker).
- TypeScript-Strict-Modus aktiv, `tsconfig.json` mit Pfad-Alias `@/*`.

**Schwächen:**
- Sehr große Komponenten (`ResultsDashboard.tsx` 1335 LOC, `HoldingsBucket.tsx` 1281 LOC, `PrivateEquityBucket.tsx` 662 LOC). Schwer wartbar, hoher Re-Render-Druck.
- Keine **Error Boundary** auf App-Ebene (`app/error.tsx` fehlt). Eine einzige Recharts-Exception killt die ganze Seite.
- Keine `app/loading.tsx` → kein Skelett während dynamischer Hydration.
- Keine `app/not-found.tsx` → Default-404 ist generisch und englisch.
- `dynamic = "force-dynamic"` in `layout.tsx` erzwingt SSR pro Request für *jede* Route — ist hier wegen CSP-Nonce nötig, aber damit verliert man jegliches Static-Edge-Caching.

### 2.2 State Management — **Note 3 (akzeptabel, eine harte Lücke)**
**Stärken:**
- `Context + useReducer` mit typisierter `Action`-Union (`SET_INPUTS` etc.) — sauber, ohne Magic Strings.
- Kein Zustand außerhalb des Reducers für Domänen-Daten.

**Schwächen — eine davon ist hart:**
- 🔴 **`AppProvider` persistiert NUR `uiMode`/`uiModeChosen` in `localStorage`**. Wenn der Banker die Seite reloadet, einen Tab versehentlich schließt, oder ein Notebook ins Energiesparen geht → **gesamte Eingabe weg** (Profile, Inputs, Portfolio, Simulationsergebnisse, Holdings).
  - In einer 90-Minuten-Beratung ein **Beratungstermin-Killer**.
- Kein „Mandant speichern / laden"-Flow.
- Dispatch-Granularität führt zu vielen Re-Renders der Top-Level-`<TabsContent>`.

### 2.3 Datenmodell und API-Design — **Note 2-3**
**Stärken:**
- Domänen-Typen (`ClientProfile`, `FinancialInputs`, `PortfolioConfig`, `SimulationResult`, `MifidProfile`) sind klar getrennt und gut benannt.
- API-Routen unter `/api/holdings/*` haben einen einheitlichen Body-Validierungsstil.

**Schwächen:**
- Keine Schema-Validierung am API-Eingang (kein `zod`/`valibot`). Man verlässt sich auf `if (!Array.isArray(...)) return 400`. OK, aber bei Bank-Standard wäre Schemas Pflicht.
- `runtime = "nodejs"` + `maxDuration = 60` für Backtest — gut. Aber kein Timeout pro Yahoo-Call → kann auflaufen.
- Keine `Cache-Control`-Header auf API-Antworten (z. B. ETag/`s-maxage`).

### 2.4 Fehlerbehandlung — **Note 4 (Hauptschmerz)**
- 🔴 `alert("PDF-Export fehlgeschlagen: ...")` in `ClientView.tsx` Zeilen 79/104. **Browser-`alert()` ist in einer Bank-App eine Sünde**: blockierend, nicht Tastatur-fokussierbar, unschön, nicht i18n-kompatibel, nicht testbar.
- 🟠 `alert("Logo > 200 KB ...")` in `AdvisorSettings.tsx` — gleiche Krankheit.
- 🟠 `console.error(...)` in `ExportPanel.tsx`/`ClientView.tsx` — User sieht nichts, IT-Ops hat keinen Logging-Pfad.
- Es gibt eine `Toaster`-Komponente (`sonner`) im Repo, aber sie ist **nicht in `layout.tsx` eingebunden** → niemand kann `toast()` rufen.

### 2.5 Security und Datenschutz — **Note 2 (solide), 1 hartes Restrisiko**
**Stärken:**
- Per-Request **CSP-Nonce + `strict-dynamic`** in `middleware.ts` — sauber, das schützt gegen XSS.
- HSTS, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy alle gesetzt (`next.config.js`).
- Keine inline-Scripts.
- Skeena-Schrift selbst gehostet — kein externes Font-Egress.
- Server-Side-Proxies für Yahoo/OpenFIGI/Frankfurter — Browser hat kein direktes externes Fetching → entspricht Bank-Egress-Policies.

**Schwächen:**
- 🔴 **Keine Authentifizierung**. Wer die URL kennt, kommt rein. Für eine Bank-App muss min. ein Auth-Wall vor (Vercel Auth, Cloudflare Access, NextAuth, etc.).
- 🟠 **Kein Rate-Limit** auf `/api/holdings/*`. Yahoo blockt nach Volumen → ein offener Endpoint ist DoS-Risiko + Vendor-Sperre.
- 🟡 `VERCEL_OIDC_TOKEN` liegt in `.env.local`. Ist nur lokal und automatisch von Vercel-CLI generiert, aber `.env.local` muss im `.gitignore` stehen (geprüft: ja).
- 🟡 Kein **Audit-Log** für Berater-Aktionen (Export, Multi-Run, Holdings-Lookup) — Bank-Compliance verlangt das.
- 🟡 Kein Logo-/Banker-Daten-Sanitizing (XSS in Eingabefeldern → wird in HTML-Export gespiegelt).

### 2.6 Performance — **Note 3**
**Stärken:**
- Engine ist algorithmisch in Ordnung (Cholesky einmal, Reuse in 10k Sims).
- Recharts wird konditional gerendert (nur bei `result != null`).

**Schwächen:**
- 🔴 **Monte-Carlo läuft auf dem Main-Thread**. 10 000 Pfade × 40 Jahre = ca. 400 000 Rechenschritte + KESt-Logik. Das blockt die UI für ~1–3 s. Im Multi-Run × 4 MiFID-Profilen wird das zu 5–10 s **mit eingefrorener UI**. Web-Worker-Auslagerung wäre Pflicht.
- 🟠 Sehr große Komponenten ohne `React.memo` / `useMemo`-Hülle für Diagramm-Daten — bei jeder Eingabe wird die `ComposedChart` neu durchgereicht.
- 🟠 `force-dynamic` global → keine Edge-Caches, jede Anfrage Cold-Path.
- 🟡 `force-cache: 'no-store'` ist nirgends explizit gesetzt — gut, aber Yahoo-Proxy-Cache ist **per Lambda-Instanz** (kein Vercel-KV), bei Cold Start → leer.

### 2.7 UX/UI und Accessibility — **Note 2-3**
**Stärken:**
- Klar gegliederte Tabs, schöne Skeena-Typografie, konsistente Tailwind-Token, rote Accent-Farben passen zur Marke.
- DE/EN i18n vollständig.
- Mode-Chooser (Classic/Pro) reduziert kognitive Last.

**Schwächen:**
- 🟠 **Keine globalen Empty-States**: Bevor Simulation gelaufen, zeigen `ResultsDashboard`/`DetailedExample` einfach `null` → User landet auf einem leeren Tab.
- 🟠 **Form-Validierung minimal**: Beträge nicht auf Plausibilität geprüft (z. B. Pension-Alter < Rentenalter, Spar-Rate negativ → Engine könnte NaN liefern).
- 🟡 **Accessibility-Labels** teils vorhanden (Radix-UI macht viel von selbst), aber Custom-`<button>` in Charts/Toggles fehlen `aria-label`.
- 🟡 **Tastatur-Navigation** durch Tabs OK (Radix), aber Slider+Inputs nicht durchgängig getestet.
- 🟡 **Farbenblindheit**: Rot-Grün-Akzente in den Buckets, kein Muster-Fallback.

### 2.8 Mobile Responsiveness — **Note 3**
- Hauptlayout ist responsive (`md:grid-cols-...`). Charts sind `ResponsiveContainer`.
- Aber: Tab-Bar mit 10–11 Tabs auf Mobile bricht (vertikale Scroll-Liste vs. Wrap unklar).
- Holdings-Tabelle (1281 LOC) ist nicht für 375 px optimiert.
- Banker-Use-Case ist primär Desktop, daher akzeptabel — aber „Demo am iPad" sollte funktionieren.

### 2.9 Edge Cases — **Note 3**
| Edge Case | Verhalten |
|---|---|
| `currentAge ≥ retirementAge` | Engine läuft mit 0-Jahren-Akkumulation; ggfs. NaN bei Diskontierung |
| `pensionStartAge > endAge` | Pension nie ausgezahlt — kein Fehler, aber unbeabsichtigt |
| `withdrawalAmount > Vermögen` | `findSustainableWithdrawal` läuft Bisektion, sollte stabil sein |
| Yahoo gibt 0 Datenpunkte zurück | Backtest-Route hat Null-Check, gibt `error` |
| Browser-localStorage voll/Inkognito | UIMode-Persistierung schluckt Fehler — OK |
| Kunde tippt 1.000.000.000 € | Recharts skaliert; aber Tausender-Format prüfen |
| Browser ohne JS / mit blockiertem Storage | App lädt, alle Inputs gehen, kein Reload |

### 2.10 Testbarkeit — **Note 4 (Hauptlücke)**
- Es existieren **2 Test-Dateien** (`sanitize.test.ts`, `clientReport.test.ts`), aber **kein Test-Runner im `package.json`**. Niemand führt sie aus.
- Engine (Monte-Carlo, KESt, PE-Bucket) hat **null Tests**. In einem Bank-Tool für Vermögensplanung ist das ein Compliance-Risiko.

### 2.11 Skalierbarkeit — **Note 3**
- Stateless Next.js + Vercel skaliert horizontal.
- Holdings-Caches per Lambda-Instanz → bei mehreren Bankern gleichzeitig wenig Cache-Hit-Quote. Kein Drama, kostet Yahoo-Calls.
- MC-Simulation Client-seitig → skaliert mit User-CPU; Server kostet 0.

### 2.12 Wartbarkeit — **Note 3**
- TypeScript strict, Biome-Lint, ESLint im Build erzwungen → gut.
- Aber: `ResultsDashboard.tsx` 1335 Zeilen ist **die Definition von schwer wartbar**. Sollte in 4–6 Sub-Komponenten aufgeteilt werden.
- Inline-Magic-Numbers (z. B. KESt 27.5, Tax-Free-Allowance) sind schon konstantenfähig in `defaults.ts`, gut.

### 2.13 Deployment / Production Readiness — **Note 3**
- Vercel-Setup OK, custom Domain OK.
- 🔴 `package.json`: `"build": "prisma generate; BUILD_DIR=.next-build next build"` — **es gibt kein Prisma in `dependencies`**. Auf Vercel funktioniert es zufällig, weil `prisma generate` nicht-existenter `prisma`-Binary `command not found` wirft, was vom `;`-Separator geschluckt wird. **Das ist Glück, kein Engineering**.
- Kein `.env.example` für Onboarding neuer Entwickler.
- Kein `README.md` im Projekt-Root mit Deploy-Anleitung (nur `DEPLOY_ANLEITUNG.md` außerhalb).

## 3. Priorisierte Issue-Liste

### 🔴 KRITISCH (Bank-Showstopper, sofort)

#### C-1 — `alert()` in Production (UX/Bank-Standard)
- **Wo:** `src/components/sections/ClientView.tsx:79`, `ClientView.tsx:104`, `AdvisorSettings.tsx:26`
- **Warum:** Browser-`alert()` ist blockierend, nicht stylebar, nicht i18n-tauglich, nicht keyboard-friendly. In einem Beratungsgespräch unprofessionell.
- **Fix:** Toast-System mit `sonner` aktivieren (Toaster in Layout, `toast.error(...)` statt `alert(...)`).

#### C-2 — Kein Persistenz-Layer für Beratungsstand
- **Wo:** `src/components/AppProvider.tsx`
- **Warum:** Banker verliert nach Browser-Reload alle Eingaben (Kundenprofil, Portfolio, Simulationsergebnisse). In einer 90-Min-Beratung katastrophal.
- **Fix:** Hinzufügen einer `sessionStorage`-Persistenz für den gesamten App-State (außer großen Trace-Objekten). Optional: Export/Import als JSON-Datei.

#### C-3 — `prisma generate` im Build-Script ohne Prisma installiert
- **Wo:** `package.json` Zeile `"build"`
- **Warum:** Verlässt sich auf Shell-Verkettung (`;`); bricht in CI mit `set -e`, irritiert neue Entwickler, signalisiert „dirty" Setup.
- **Fix:** `prisma generate` entfernen.

#### C-4 — Keine globale Error-Boundary
- **Wo:** `src/app/` (kein `error.tsx`)
- **Warum:** Eine einzige Exception (z. B. Recharts mit NaN-Daten) crasht die gesamte Seite ohne Fehler-UI für den Banker.
- **Fix:** `app/error.tsx` mit user-freundlichem Fallback (DE+EN), inkl. „Reset" und „Reload"-Buttons.

### 🟠 HOCH (vor erstem Bank-Pilot)

#### H-1 — Monte-Carlo blockt Main-Thread
- **Wo:** `src/components/sections/SimulationPanel.tsx:81–95` und `src/lib/engine/montecarlo.ts`
- **Warum:** UI friert ein, Progress-Bar springt nicht flüssig, Multi-Run dauert spürbar.
- **Fix:** Web-Worker (`new Worker(new URL("./mc.worker.ts", import.meta.url))`) für `runMonteCarloSimulation`. Einfacher Schritt 1: `requestIdleCallback`-Yields nach jedem 1000. Pfad. Mittlerer Aufwand.

#### H-2 — Kein Auth-Wall
- **Wo:** App-Ebene (`middleware.ts`)
- **Warum:** Bank-App ohne Login = Compliance-Verstoß, falls Kundendaten irgendwo ankommen.
- **Fix-Vorschlag:** Vercel Authentication (Project-Setting) als simpler Wall, oder NextAuth + Microsoft-Entra-Integration. **Annahme:** Heute durch URL-Geheimhaltung „geschützt" — explizit dokumentieren als Restrisiko.

#### H-3 — Kein Rate-Limit auf `/api/holdings/*`
- **Wo:** `src/app/api/holdings/{search,quote,backtest,...}/route.ts`
- **Warum:** Offener Endpunkt → Vendor-Sperre durch Yahoo + DoS-Vektor.
- **Fix:** Token-Bucket pro IP (in-memory pro Lambda reicht für ersten Schritt). Vercel-KV oder Upstash für globalen Schutz.

#### H-4 — Keine Tests im Build
- **Wo:** `package.json`
- **Warum:** Vorhandene `*.test.ts` werden nie ausgeführt → falsches Sicherheitsgefühl.
- **Fix:** `vitest` einsetzen, `bun test` als Skript, mind. die Engine-Schichten unit-testen (KESt, Cholesky-Korrelation, PE-Bucket).

#### H-5 — Keine Form-Validierung an Eingaben
- **Wo:** `FinancialInputs.tsx`, `ClientProfile.tsx`, `PortfolioBuilder.tsx`
- **Warum:** User kann negative Sparraten, Pension-Alter > End-Alter, Bucket-Allokationen ≠ 100 % eingeben → Engine produziert NaN/sinnlose Pfade.
- **Fix:** `zod`-Schemas oder Inline-Guards mit deutschen Fehlermeldungen.

#### H-6 — `force-dynamic` zwingt jede Route in SSR
- **Wo:** `src/app/layout.tsx`
- **Warum:** Notwendig für CSP-Nonce, aber führt zu Latenz & 0 % Edge-Cache.
- **Fix:** Akzeptieren als bewussten Trade-Off; in `layout.tsx` als Kommentar dokumentieren (ist bereits da). Zusätzlich `revalidate = 0` nur in API-Routen, nicht global.
